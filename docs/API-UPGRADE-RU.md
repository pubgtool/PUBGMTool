# Безопасное обновление API Line без сброса данных 6.0

Это инструкция для подготовки и передачи обновления API. Она **не подключается к VPS и не выполняет развёртывание**. Имя сервиса, каталог приложения, пользователь процесса и фактические пути данных здесь намеренно не предполагаются: сначала установите их по конфигурации уже работающего экземпляра.

## Что входит и что сохраняется

Запустите из корня репозитория `bash scripts/package-api-update.sh`. Скрипт создаёт `artifacts/Line-API-offline-update.tar.gz` и файл контрольной суммы рядом. В архив попадают только отслеживаемые Git файлы `server/package.json`, `server/package-lock.json`, `server/src/**`, `server/test/**`, `server/scripts/hash-admin-password.mjs` (если файл отслеживается), а также созданный манифест с ревизией и временем сборки. Скрипт отказывается собирать пакет, пока `server/package.json` или lock-файл содержат `firebase-admin`/`@firebase`. `node_modules` и зависимости в архив не включаются.

Архив не содержит и не заменяет APK, конфигурацию процесса, переменные окружения, секреты, Firebase-ключи, TLS-сертификаты, настройки домена/Caddy/LiveKit, номера/идентичности, ключи и данные приложения. Он также не содержит постоянные хранилища API. **Не очищайте и не создавайте заново данные API и приложения, не меняйте их пути и не запускайте пакет поверх неизвестного каталога.** Старые данные должны оставаться на прежнем месте; сохраняйте их владельца и права доступа.

В исходном API переменная `DATA_FILE` задаёт JSON-хранилище идентичностей (по умолчанию `server/data/identities.json`). От неё по умолчанию образуются три отдельные записи: `${DATA_FILE}.admin.json`, `${DATA_FILE}.mailbox.json` и `${DATA_FILE}.push.json`; при заданных `ADMIN_DATA_FILE`, `MAILBOX_FILE` или `PUSH_TOKEN_FILE` используются именно указанные пути. До обновления выясните эффективные значения всех четырёх путей локально на VPS. Пути из примера репозитория **не являются подтверждением** путей живого сервера.

Есть два ожидаемых исключения из сохранения представления данных. Новая версия может записывать необязательное `displayName` в запись идентичности. Старый API 6.0 не использует это поле и при последующей записи идентичностей может его отбросить; не запускайте старый бинарный код поверх новых данных без отдельной проверки отката. Кроме того, push-токены FCM не являются UnifiedPush endpoint-ами: сервер принимает HTTPS endpoint с topic только из origin-ов `PUSH_ALLOWED_ORIGINS`. На старте недопустимые/старые endpoint-ы отбрасываются из активного push-store. Сделайте защищённую копию исходного `PUSH_TOKEN_FILE`; старые FCM-токены пригодны только как архив, клиентам нужно зарегистрировать новые endpoint-ы. Если требуется буквально оставить эти токены в активном файле, не запускайте обновление до согласования миграции.

## Сборка и передача из Windows

В Bash-окружении с `git`, `tar` и `sha256sum` выполните в корне проекта:

```bash
bash scripts/package-api-update.sh
```

Скрипт берёт исходники из этого рабочего дерева: манифест показывает базовую Git-ревизию и помечает, отличаются ли включённые отслеживаемые файлы от неё. Перед передачей сверьте ревизию и SHA-256. В PowerShell можно вычислить хеш так:

```powershell
(Get-FileHash .\artifacts\Line-API-offline-update.tar.gz -Algorithm SHA256).Hash
```

Сравните результат без учёта регистра с первой колонкой `.tar.gz.sha256`, затем скопируйте **оба** файла по уже настроенному SSH-доступу, заменив значения на ваши:

```powershell
scp .\artifacts\Line-API-offline-update.tar.gz .\artifacts\Line-API-offline-update.tar.gz.sha256 SSH_USER@VPS_HOST:~/
```

Замените `SSH_USER` и `VPS_HOST` фактическими значениями. Не публикуйте архив вместе с резервными копиями данных или файлами окружения. Сам архив — исходники сервера, а не полностью автономная установка: он не включает Node.js, npm или `node_modules`; `npm ci` требует доступного npm-кэша либо реестра пакетов.

## Проверка до остановки API

На VPS сверяйте загруженный архив по SHA-256, распакуйте его **в отдельный закрытый staging-каталог**, затем из `staging/server` проверьте версию Node.js (проект требует Node `>=24`), выполните `npm ci` и `npm test`. Это не команды развёртывания и не должны обращаться к хранилищам живого API. Если установка зависимостей или тесты не прошли, живой процесс не останавливайте.

До окна обслуживания определите точный менеджер процессов, экземпляр API, рабочий каталог, пользователя и конфигурацию. Если сервисом действительно управляет systemd, сначала найдите фактическое имя сервиса (`systemctl list-units --type=service --all --no-pager`); для уже установленного имени можно локально посмотреть только `FragmentPath`, `User`, `WorkingDirectory` и `EnvironmentFiles` через `systemctl show`. Не выводите и не пересылайте значения переменных окружения, содержимое env-файлов или командные строки с секретами. Для включения UnifiedPush оператор может задать `PUSH_ALLOWED_ORIGINS` как список HTTPS origin-ов (без путей/topic); hostname ntfy должен быть публичным DNS-именем, которое разрешается только в публичные адреса. Это отдельная необязательная конфигурация push, не замена текущему адресу API. Для другого менеджера используйте его фактическую конфигурацию. Не угадывайте имя сервиса, каталоги, переменные или команду перезапуска.

## Сохранение данных и переключение кода

После успешной проверки заранее назначьте короткое окно недоступности. Остановите только подтверждённый процесс API — не Caddy, LiveKit, TURN или VPS. Пока API остановлен, снимите защищённую резервную копию каждого существующего файла из эффективных `DATA_FILE`, `ADMIN_DATA_FILE`, `MAILBOX_FILE` и `PUSH_TOKEN_FILE`; если используются значения по умолчанию, вычислите пути по правилам выше. Храните копию вне веб-каталога с ограниченными правами (не шире `0600`) и не помещайте её в пакет, чат, Git или публичное хранилище. Не редактируйте и не заменяйте эти файлы при установке кода.

Установите проверенный код в фактический каталог/механизм выпуска уже работающего API, сохранив его пользователя и **все** действующие настройки, затем запустите тот же процесс тем же менеджером. Изменение пути `DATA_FILE`, сброс хранилища, повторная регистрация пользователей и обновление Caddy/LiveKit для этого пакета не нужны. Во время остановки клиенты не смогут связаться с API; архив не меняет лимит или срок хранения сообщений. В текущей реализации отложенный mailbox хранит зашифрованные конверты с TTL до 7 дней, максимум 100 сообщений на получателя и 1 000 всего; `queued` само по себе не подтверждает получение.

После запуска проверьте журнал менеджера без вывода секретов и выполните обычное подключение совместимого тестового клиента через уже существующий адрес и сертификат. Убедитесь, что прежний аккаунт и номер доступны, настройки администратора на месте, а тестовое офлайн-сообщение принимается после переподключения адресата. Не проверяйте это удалением приложения или его данных. Если проверка не прошла, остановите API и восстановите предыдущую **копию кода** тем же способом. Не восстанавливайте резервные данные поверх файлов автоматически: после запуска новая версия могла записать туда новые сообщения или подтверждения.

## Границы и неподтверждённые условия

- Обновление сервера само по себе не обновляет APK; возможности фоновых уведомлений требуют совместимого клиента и отдельно настроенного поддерживаемого push-провайдера. Архив не переносит клиентские настройки/токены и не настраивает провайдера.
- Долговременная очередь относится к сообщениям, а не к звонкам. В текущем серверном тесте офлайн-приглашение на звонок требует push-токен получателя; состояние вызова хранится в памяти API и теряется при его перезапуске. Это не сохраняемый офлайн-звонок и не гарантия установления медиа-соединения без подключения клиентов.
- Для фонового пробуждения нужна совместимая версия приложения и настроенный UnifiedPush-дистрибьютор; собственный ntfy-хост — отдельная конфигурация только при его выборе. Это не нужно для хранения сообщений до переподключения, не входит в исходный архив и не должно менять адрес/идентичность существующего API, Caddy или LiveKit. Не добавляйте Firebase credentials в пакет.
- Репозиторий описывает шаблон native-process развёртывания, но не подтверждает, что конкретный VPS использует systemd, конкретные пути или что обновление уже выполнено. Имя текущего сервиса, его секретные переменные, права на живые файлы и доступность резервной копии должен проверить оператор на самом сервере.
- Архив — переносимый пакет исходников с lock-файлом, но не air-gapped образ: зависимости не вложены. Публичный production-сервер, подпись APK и фактическая доставка push этим документом не проверяются.

## Источники в репозитории

- `server/src/index.js` — пути JSON-хранилищ, проверки mailbox и его лимиты, запуск API.
- `server/package.json` — требование Node.js `>=24` и команды установки/тестирования.
- `server/test/signaling.test.js`, `server/test/prekeys.test.js` — изолированные серверные тесты.
- `docs/ANDROID-UNIFIEDPUSH.md` — требования клиента/distributor, протокол endpoint-а и необязательный ntfy.
- `deploy/README.md`, `docs/SERVICE-SETUP-RU.md` — шаблон native-process развёртывания и предупреждение, что он не подтверждает реальный VPS.
- `README.md`, `docs/ARCHITECTURE.md` — границы протокола 6.0/7 и состояние вызовов/mailbox.
